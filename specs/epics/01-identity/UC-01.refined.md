# UC-01 (refined) — Sign in with email and password

> Refined from `specs/use-cases/UC-01-sign-in.md` (verbatim, unchanged). Folds in the BA's answers
> from `questions_for_ba.md` and resolves the product TBDs. Architecture questions stay open in
> `epic.md` (token shape/expiry, the role-enum location, keeping the login response shaped for a
> future challenge step, the `auth:IUserRepository` cross-epic edge).

**Actor**: Member, Agent, Admin (any registered user)
**Module**: Identity / Authentication

## Description

The Helpdesk is a closed system — there is no public sign-up, every account is created by an
administrator. Signing in is therefore the front door for everyone. A user enters their email and
password, and if those are correct the system issues a session token that every other use case
assumes.

We kept v1 deliberately simple: a single email+password exchange that returns a signed bearer
token. We discussed adding a second factor (email OTP or an authenticator app) but decided to defer
it — the audience is internal support staff behind a VPN, and the product owner wanted the smallest
thing that works first. The token shape and expiry live with the auth slice; this UC ends the moment
a valid session is issued.

## Main flow

1. User opens the sign-in screen and submits credentials. The form has fields:
   - **Email** (required, email; matched case-insensitively against the stored account).
   - **Password** (required, free text). The minimum length is **8 characters** — the committed v1
     policy and the only password rule (no maximum, no complexity requirements). It is enforced as a
     pre-flight gate: an attempt shorter than 8 characters is rejected before the store is touched.
2. System validates the credentials:
   - Looks up the account by a lower-cased email.
   - Verifies the password against the stored hash (we use argon2id).
   - Confirms the account is active.
3. On success, System issues a signed bearer token (a JWT carrying the user id, role, and an expiry)
   and returns it to the client. A successful sign-in also clears the account's failed-attempt
   counter (see A3).
4. System lands the user on their home view — the open-tickets list for Agents and Admins.

## Alternative flows

- **A1**: Wrong password. System returns a generic "invalid email or password" — we deliberately do
  not reveal whether the email exists. An unknown email still runs a dummy hash so response timing
  doesn't leak account existence.
- **A2**: Account is deactivated (`is_active=false`). Credentials may be correct but System refuses
  with a distinct "account inactive" error; the user must contact an admin. This message is exempt
  from the non-disclosure rule: that rule is scoped to credential validity (unknown-email and
  wrong-password must be indistinguishable) and does not extend to a deactivated-but-valid account —
  a deactivated internal user is told to contact an admin rather than left guessing.
- **A3**: Too many failed passwords. The account is locked after **5 failures inside a 10-minute
  window** and stays locked for **15 minutes**. These are the agreed v1 defaults but remain
  config-driven, not hard-coded, so security can retune them without a code change. Lockout is
  tracked **per account** (against the looked-up user), not per request source / IP — internal staff
  share egress IPs, so the account is the meaningful unit, and the User account therefore carries a
  failed-attempt counter. The counter clears on a successful sign-in; it also resets when the
  10-minute window lapses with no new failure, and the 15-minute lock auto-releases (the counter
  starts fresh afterwards).

## Business Rules

- No self-service registration — accounts exist only because an admin created them.
- Credentials are validated case-insensitively on email but exactly on password.
- A password attempt must be at least 8 characters; this is both a pre-flight gate (rejected before
  hitting the store) and the stated v1 password policy. There is no maximum length and no complexity
  rule in v1.
- We never reveal whether an email is registered — same generic error and same response timing for
  unknown-email and wrong-password. This non-disclosure rule is scoped to credential validity; it
  does not apply to the deactivated-account message (A2).
- The bearer token is signed with the server-side key; clients send it as `Authorization: Bearer …`.

## Notes

- Password reset / "forgot password" is intentionally **not** in v1 — a forgetful user is handled by
  an admin editing the account. This deferral is confirmed: the refined UC carries no reset flow.
  Flag for a future UC if self-service reset is ever prioritized.
- A second factor (OTP) is out of scope for v1 but likely a fast follow — keep the login response
  shaped so a challenge step could slot in later without breaking clients. OTP staying out of v1 is
  confirmed.
