# UC-03 (refined) — Manage labels

> Refined from `specs/use-cases/UC-03-manage-labels.md` (verbatim, unchanged). Folds in the BA's answers
> from `questions_for_ba.md` and resolves the product TBDs. Architecture questions stay open in `epic.md`
> (how/where `usage_count` is incremented; Label-as-aggregate vs a denormalized counter on Ticket; whether
> unarchive is a dedicated action or a flag on update).

**Actor**: Admin (mutations: create, update, archive, unarchive, delete); Member, Agent (read)
**Module**: Support / Reference data

## Description

Labels are the small, shared vocabulary agents stick on tickets to slice the queue — `billing`,
`urgent`, `bug`, and so on. They are reference data: a short, admin-curated list that everyone reads
but only admins change. This UC is the CRUD around that list. It is almost pure CRUD, which makes it
a good first end-to-end exercise of the pipeline.

We debated deleting versus archiving. The team decided a label that is still stuck on tickets must
not silently vanish, so deletion is blocked once a label is in use; archiving is the soft path that
hides a label from the picker without breaking the tickets that already carry it, and unarchiving
brings it back. A small `is_pinned` flag lets admins float the handful of labels they use constantly
to the top of the picker — it is a plain presentation hint, not a rule.

## Main flow (create)

1. Admin opens the labels admin screen and submits the "new label" form. The form has fields:
   - **Name** (required, free text; non-empty after trimming whitespace, maximum 50 characters, no
     character restrictions — labels are meant to be short and human-readable).
   - **Pinned** (optional boolean; defaults off — a pinned label sorts to the top of the picker).
2. System validates the input and creates the label with `usage_count = 0`, not archived. The name is
   accepted even if another label already uses it — there is no uniqueness check in v1.
3. System returns the new label id and refreshes the list.

## Main flow (update)

1. Admin edits a label's name or pinned flag. Both fields are optional on update (PATCH semantics —
   only the supplied fields change). A supplied name follows the same constraints as on create
   (non-empty after trimming, maximum 50 characters) and is not checked for uniqueness against other
   labels.
2. System looks up the label by id and applies the changes.

## Main flow (list)

1. Any authenticated user requests the labels. By default archived labels are hidden; an
   `include_archived` flag returns them too.
2. System returns the matching labels plus a total count.

## Main flow (archive / unarchive)

1. Admin archives a live label: the system hides it from the picker without affecting tickets that
   already carry it. Archiving is the soft alternative to deletion and the only path for a label that
   is still in use (`usage_count > 0`).
2. Admin unarchives an archived label: the system brings it back into the picker.

## Alternative flows

- **A1**: Update or delete targets an id that does not exist. System rejects with a not-found error.
- **A2**: Delete a label whose `usage_count > 0` (still stuck on tickets). System refuses with a
  conflict error — the admin must archive it instead.
- **A3**: Delete a label that is archived. System refuses with a conflict error; an archived label is
  already hidden and is kept for the tickets that reference it.
- **A4**: Delete a live, unused label (`usage_count = 0`, not archived). System removes it.

## Business Rules

- Only Admins create, update, archive, unarchive, or delete labels; Members and Agents may only read
  them.
- A label name is required and non-empty after trimming whitespace, at most 50 characters, with no
  character restrictions. Names are not unique in v1 — two labels may share the same name, and neither
  create nor update checks for an existing name. (Flagged for a future UC if duplicate names become a
  support problem.)
- A label cannot be deleted while in use (`usage_count > 0`) or while archived — archive is the soft
  alternative to deletion.
- Archiving hides a label from the picker without affecting tickets that already carry it;
  unarchiving brings it back. Both archive and unarchive are admin actions in v1.
- `usage_count` is system-maintained: a new label starts at 0, and within this UC the counter is
  read-only — an admin never sets or edits it directly. It moves only through the future
  apply/remove-label-on-a-ticket flow.
- `is_pinned` is a presentation hint only (sort order), not an access or lifecycle rule.
