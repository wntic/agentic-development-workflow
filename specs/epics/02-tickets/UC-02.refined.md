# UC-02 (refined) — Create a support ticket

> Refined from `specs/use-cases/UC-02-create-ticket.md` (verbatim, unchanged). Folds in the BA's answers
> from `questions_for_ba.md` and resolves the product TBDs. The architecture question — how the status
> field is modeled going forward (free enum vs a guarded transition table) — stays open in `epic.md` for
> the architect; this refined UC only fixes the product-visible behaviour.

**Actor**: Member, Agent (any authenticated user)
**Module**: Support / Tickets

## Description

A ticket is the unit of work in the Helpdesk: someone reports a problem, an agent picks it up, and it
moves through a small lifecycle until it is resolved. This UC covers the very first step — opening a
ticket. Any authenticated user may open one; assignment and triage are separate concerns.

Every new ticket starts in a single well-known state (`OPEN`). In v1 `OPEN` is the only creation state:
the user cannot pick a state, and there is no draft or alternate initial state. The post-creation
lifecycle (the states a ticket can move through after creation) is a separate, later UC. Assignment is
optional at creation time; an unassigned ticket simply sits in the queue.

## Main flow

1. User opens the "new ticket" form and submits it. The form has fields:
   - **Title** (required, free text, 3–200 chars inclusive — 3 chars allowed, 200 chars allowed;
     length is measured after trimming surrounding whitespace).
   - **Description** (required, free text; must be non-empty after trimming whitespace; no maximum
     length in v1 — any non-empty text is acceptable).
   - **Assignee** (optional; an Agent's user id — defaults to unassigned).
2. System validates the input:
   - Title length is within bounds (3–200 inclusive, measured after trimming surrounding whitespace).
   - Description is non-empty after trimming whitespace.
   - If an assignee is supplied, it must reference an existing user with the Agent role.
3. System creates the ticket in the `OPEN` state, stamps it with the creating user — always the
   authenticated user who submitted the form — and persists it.
4. System returns the new ticket id and shows the ticket detail view.

## Alternative flows

- **A1**: Title is blank, too short (fewer than 3 chars after trimming whitespace), or too long (more
  than 200 chars after trimming). System rejects with a validation error naming the field; no ticket
  is created.
- **A1b**: Description is blank or whitespace-only (empty after trimming). System rejects with a
  validation error naming the field; no ticket is created.
- **A2**: The supplied assignee is not an Agent (or does not exist). System rejects with a "cannot
  assign to this user" error.

## Business Rules

- Any authenticated user may open a ticket; you do not need the Agent role to be a reporter.
- The reporter stamp is always the authenticated user who submitted the form. In v1 a user can only
  open a ticket on their own behalf; reporting on behalf of someone else is not supported.
- A new ticket always starts in `OPEN`; `OPEN` is the only creation state in v1.
- Only Agents can be assignees; a Member can report but not be assigned.

## Notes

- Re-assignment, status transitions, and resolution are out of scope for this UC — they ride on the
  ticket aggregate this UC creates.
- Attachments / file upload are out of scope for v1: a ticket is created with Title, Description, and an
  optional Assignee only; there is no way to attach a file at creation time (deferred to a later UC).
- How the status field is modeled going forward (a free enum vs a guarded transition table) is an
  architecture decision left open in `epic.md` for the architect; the team's intent is to retain the
  flexibility to add states later. This refined UC fixes only the product-visible fact that creation
  state is `OPEN`.
