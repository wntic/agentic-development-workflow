# UC-15 (refined) — Search meetings by content

> Refined from `specs/use-cases/UC-15-search-meetings.md` (verbatim, unchanged). Folds in the BA's

**Actor**: Member, Admin (any signed-in user)
**Module**: Meetings / Search

## Description

Beyond the structured library filters (UC-14), users want to ask "which meeting was that where we
talked about the Q3 pricing change?" — semantic search over what was actually *said*, not just titles.
This is why UC-13 embeds each transcript into a vector store: a search query is embedded the same way
and matched by similarity against the workspace's indexed transcripts.

The user types a natural-language query; the system embeds it, finds the most similar meeting
transcripts in the workspace, and returns those meetings ranked by relevance. It's a discovery tool,
not an exact-match filter.

For v1, a search returns up to **10** results (top-k), a deployment-config knob. A relevance/similarity
cutoff is applied so weak matches are dropped: a search that finds nothing genuinely relevant returns
**fewer or zero results** rather than 10 weak ones (returning irrelevant matches erodes trust worse
than an honest "no results"). The product-visible behavior is "only show what's actually relevant"; the
exact threshold **value** is a config knob for the ML team to calibrate. Hybrid (semantic + keyword)
search is out of scope for v1 — semantic only.

## Main flow

1. User types a search query (free text).
2. System embeds the query text into a vector.
3. System searches the workspace's vector index for the most similar transcripts (top-k, default 10),
   getting back meeting ids and similarity scores, dropping any match below the configured relevance
   threshold.
4. System loads those meetings and returns them ranked best-first: each result carries the meeting id,
   title, status, and the similarity score. With the threshold applied, a query may legitimately return
   fewer than top-k results, or zero.

## Alternative flows

- **A1**: Nothing is similar (or the workspace has no indexed meetings yet, or every candidate fell
  below the relevance threshold). System returns an empty result list — not an error.
- **A2**: A meeting matched in the vector index but its row was since deleted (race). System
  **silently skips** it from the results — no error is shown to the user. A hit pointing at a missing
  row is an internal consistency gap, not a searcher error; this is defensive (deletion isn't a v1
  feature) and also covers the index-vs-row race generally.
- **A3**: The query is empty/whitespace. System rejects with a validation error (don't embed empty
  text).

## Business Rules

- Search is tenant-scoped: the vector index is queried with the token's `workspace_id`, so results
  never cross workspaces (the index entries were written tenant-scoped in UC-13).
- Results are ranked by similarity, best first; a configurable top-k (default 10) bounds the count, and
  a configurable relevance threshold drops weak matches (so the result set may be smaller than top-k or
  empty).
- Only READY meetings have transcripts indexed, so only they can match (UPLOADED/PROCESSING/FAILED
  were never indexed).

## Notes

- top-k (default 10) and the relevance/similarity threshold are config, not hard-coded; the threshold
  value is ML-calibrated.
- This read hits the vector store (a client-style store), not the relational filter path of UC-14 —
  they're deliberately different mechanisms.
- Out of scope: hybrid search, highlighting the matching passage, search-within-a-meeting. Later UCs.
