# UC-14 (refined) — Browse and open meetings

> Refined from `specs/use-cases/UC-14-browse-meetings.md` (verbatim, unchanged). Folds in the BA's
> answers from `questions_for_ba.md` and resolves the product TBDs. Architecture questions stay open in

**Actor**: Member, Admin (any signed-in user)
**Module**: Meetings / Library

## Description

The meeting library is the home screen: a paged, filterable list of the workspace's meetings, and the
detail view you get when you open one. The list shows enough to scan (title, status, when it was
created, whether it has action items); the detail view shows the full summary and the action items.

This is a straightforward read screen, but it's where pagination and filtering matter — a busy
workspace has hundreds of meetings. We want to filter by status (e.g. only READY ones, or find the
FAILED ones to retry) and by a created-date range, and to sort by newest-first (default) or by title.
The default page size is **20** (deployment config, not a magic number); a client-supplied page size is
capped at a maximum of **100** (also config) so a caller cannot request an unbounded page.

We considered a free-text filter on the title here, but decided real content search is a separate,
semantic thing (UC-15) — this screen's filtering is structured (status, dates), not search.

## Main flow (list)

1. User opens the library. The client may pass filters:
   - **Status** (optional, multi-valued — any of UPLOADED / PROCESSING / READY / FAILED).
   - **Created after** / **Created before** (optional, dates).
   - **Sort** (optional — newest-first by created date is the default; title A–Z is the alternative).
   - **Page** (optional — page number / size for pagination; default size 20, max 100).
2. System returns the matching meetings for the user's workspace, paged, plus the total count so the
   client can render pagination. Each row carries: id, title, status, created-at, created-by, and how
   many action items it has.

## Main flow (detail)

1. User opens one meeting by id.
2. System returns the full meeting: id, title, status, created-at, created-by, the summary text (empty
   until processed), and the list of its action items (each: id, title, status).

## Alternative flows

- **A1**: No meetings match (empty workspace or over-narrow filters). System returns an empty page
  with total 0 — not an error.
- **A2**: Detail for a meeting id that doesn't exist or is in another workspace. System returns 404
  (cross-tenant is indistinguishable from not-found).
- **A3**: An out-of-range page (past the end). System returns an **empty page** with the real total
  count (no error) — a page past the end is a normal navigation state, so the client can detect it
  overshot and recompute.

## Business Rules

- Every list and detail read is tenant-scoped to the token's `workspace_id` — never a request param.
- The list is paginated; the response always includes the total matching count (for the pager). The
  default page size is 20 and the maximum client-supplied page size is 100 (both deployment config).
- Sort options are a closed set (created-date, title) — not an arbitrary client-supplied column.
- A meeting's action-item count is shown in the list; the full action items only in detail.

## Notes

- The list and the detail are two reads; the detail joins in the action items (a meeting's action
  items are read by meeting id).
- Default sort newest-first; default page size 20, max 100 (all config). Don't hard-code a magic
  number in a body.
- Out of scope here: bulk operations, export (export is UC-17 if/when written), content search (UC-15).
