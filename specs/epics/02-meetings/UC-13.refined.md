# UC-13 (refined) — Process a recording into a summary and action items

> Refined from `specs/use-cases/UC-13-process-recording.md` (verbatim, unchanged). Folds in the BA's
> answers from `questions_for_ba.md` and resolves the product TBDs. Architecture questions stay open in
> `epic.md`.

**Actor**: Member, Admin (any signed-in user); System (the AI pipeline)
**Module**: Meetings / Processing

## Description

After a recording is uploaded (UC-12) it's just bytes and a title. This UC runs the AI pipeline that
makes it useful: transcribe the audio, summarize the transcript, pull out action items, and index the
transcript for semantic search (UC-15). When it's done the meeting flips to READY and the summary +
action items are visible (UC-14).

For v1 this is a **synchronous** operation the client triggers explicitly after upload (a separate call
from UC-12) — the user hits "process" and waits. We know that's not how it should work long-term (a
30-minute recording can't block an HTTP request), and async/queued processing is the obvious next step,
but the team wanted the pipeline correct before making it async. Async processing is deferred to a
future UC.

The AI steps lean on external models: transcription (Whisper-class), summarization + action-item
extraction (an LLM), and embeddings (for search). These are capabilities behind interfaces so the
specific vendor is swappable. (Embedding chunking strategy is an architecture/ML refinement left for
the architect — see `epic.md`; for v1 assume the whole transcript is embedded as one vector.)

The hard architecture question is **partial failure across two stores** (the meeting + action items in
Postgres, the embedding in the vector store, no distributed transaction) — that remains open for the
architect; see `epic.md`. The product-visible behavior for v1 is that on any pipeline failure the
meeting is marked FAILED and the user may retry.

## Main flow

1. User (or client) requests processing for a meeting they own (by meeting id).
2. System loads the meeting; it must be in UPLOADED (or FAILED, for a retry) status. It marks the
   meeting PROCESSING.
3. System fetches the audio bytes from blob storage (the stored key).
4. System transcribes the audio to text (transcription capability).
5. System summarizes the transcript and extracts a list of action items (the summarization capability
   returns both a prose summary and zero-or-more action-item titles).
6. System embeds the transcript and indexes it in the vector store under the meeting (and workspace,
   for tenant-scoped search).
7. System updates the meeting: status **READY**, the stored summary and transcript; and creates one
   action item per extracted title (status OPEN, linked to the meeting).
8. System returns the updated meeting (status READY, the summary).

## Alternative flows

- **A1**: The meeting id doesn't exist (or isn't in the caller's workspace). System returns 404
  (cross-tenant access is indistinguishable from not-found, on purpose).
- **A2**: The meeting is already READY (already processed). System **refuses** with a validation error
  — only meetings in UPLOADED (first run) or FAILED (retry) may be processed. Nothing is overwritten;
  the existing summary, transcript, and action items are preserved. (Re-process-on-demand / overwrite is
  a future UC if customers ask.)
- **A3**: Any AI step fails (transcription, summary, or embedding errors / times out). System marks
  the meeting **FAILED** and surfaces a processing error; the user may retry (back to step 1). No
  partial summary is shown.
- **A4**: Transcription returns empty (silent/corrupt audio). System marks the meeting **FAILED** (an
  empty transcription means there is nothing useful to show, so READY-with-empty-summary would mislead
  the user); the user may retry or re-upload a better recording. This also covers the
  non-audio/unsupported-file case from UC-12 (a file that isn't real audio fails here and lands FAILED).

## Business Rules

- Only a meeting in the caller's workspace can be processed (tenant scoping, derived from the token).
- A meeting's lifecycle is UPLOADED → PROCESSING → READY, with → FAILED reachable from PROCESSING and
  retry from FAILED → PROCESSING. Processing is permitted only from UPLOADED or FAILED; triggering it
  on a READY meeting is refused (A2). We are **not** building a rigid state-machine guard table in v1
  (the team wants flexibility to add states like ARCHIVED later — applies to the status field
  generally).
- Action items are created only by this pipeline in v1 (no manual add). Each belongs to one meeting.
- The vector index entry is tenant-scoped so semantic search (UC-15) never crosses workspaces.

## Notes

- Two-store write (Postgres + vector store) with no distributed tx — see Description; the accepted v1
  answer is "FAILED on error, retry may re-index". Architect to confirm (see `epic.md`).
- The transcript can be large; we store it in the meeting row for v1 (revisit if it bloats the table).
- The summarization capability returns a structured result (summary text + action-item titles) — keep
  that one round-trip rather than two model calls.
- Out of scope: speaker diarization, per-section summaries, multi-language. Flag for later UCs.
