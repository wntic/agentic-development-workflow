# Workflow v3 — спека в Markdown, детерминизм в гейтах

Дизайн-документ третьей итерации воркфлоу. Предшественник — `codegen_workflow_spec.md`
(v2: YAML-манифест + валидатор + scaffolder/implementer по DAG). Этот документ — источник
правды для v3; он написан как ТЗ, по которому воркфлоу реализуется без дополнительного
контекста. Статус v2: доказан end-to-end (см. `notes/pipeline_dryrun_feedback.md`),
заархивирован в истории `main`; v3 строится в этой ветке.

**Ревизия:** документ прошёл адверсариальное дизайн-ревью пятью независимыми зондами
(~55 находок) ДО имплементации — реестр находок и решений в `notes/15_v3_design_review.md`.
Ключевые последствия ревью: enforcement перевёрнут с prevention-хуков на post-hoc сверку
с git-baseline (S8), введена модель «один change = одна ветка» (S9), названы владельцы
швов, которые в v2 держал scaffolder+манифест (Interface sketch, removal, миграции,
bootstrap), и четыре собственных must-hold правила v3 получили детерминированные гейты.

## §0. Мотивация: два провала и их настоящие причины

v1 (генератор) и v2 (манифест + агенты) споткнулись об одни и те же два камня:

**Провал 1 — схема спеки переобучалась под референсное приложение.** Каждое новое приложение
требовало расширения схемы; три раунда аудита скиллов (~80 находок «заморозили фичу одного
приложения как универсальную») и 25 находок dry-run'а — это цена поддержки жёсткой схемы.
*Диагноз:* схема — неправильная **точка приложения строгости**. Строгий формат нужен там, где
проверяется результат, а не там, где описывается намерение. Индустрия пришла к тому же:
все выжившие инструменты (Spec Kit, Kiro, OpenSpec, SPEC.md-подход Anthropic, AGENTS.md у
OpenAI) используют секционированный свободный Markdown; жёсткие DSL живут только в рисёрче.

**Провал 2 — агенты нарушали правила, записанные в скиллах.** *Диагноз:* правило в прозе —
совет, а не ограничение; у Spec Kit задокументирован идентичный случай (constitution.md
запрещал try/catch — агент писал их всё равно). Смена формата спеки это НЕ лечит. Лечит
перенос каждого must-hold правила из прозы в **детерминированный гейт**. Дизайн-ревью
добавило вторую половину диагноза: **prevention-гейт (hook «нельзя сделать X») дыряв по
построению** — файл можно мутировать через shell, Write вместо Edit, conftest, правку самого
гейта. Надёжна только **post-hoc сверка результата с git-baseline**, которую агент не может
обойти, потому что она не запрещает действие, а обесценивает его результат. v2 уже наполовину
знал это (A3 — «детерминизм живёт в верификации»); v3 доводит до конца: детерминизм живёт
в верификации, и сама верификация проверяет целостность своих входов.

Отсюда спинной хребет v3, в одну строку:

> **Спека — свободный Markdown для человека и ориентации агента. Критерии приёмки — чеклист,
> который агенты могут только прощёлкивать с машинно-проверяемым доказательством. Все
> must-hold правила — детерминированные гейты, а доверие держит gate, сверяющий результат
> с git-baseline. Цикл: тесты → код → запуск → сверка с критериями → итерация; один change —
> одна ветка, main всегда зелёный.**

Что переживает из PRINCIPLES.md: A1 (слои не смешиваются — в новой формулировке §1), A3, A4,
C1–C7 (скиллы; C5 — в форме §7-суррогата), D1 (мало ролей), D3 (anti-collusion), F1
(brownfield-first). Что уходит: A2 и вся B-серия (манифест) — их заменяет S-серия (§11).

## §1. Три слоя v3

| Слой | Что это | Где живёт |
|---|---|---|
| **Знание** | как писать артефакт (house style) | `.claude/skills/` — после ревизии §7 |
| **Спецификация** | что нужно сделать и как проверить | `specs/` — Markdown, §2–§3 |
| **Enforcement + оркестрация** | кто что делает, что запрещено, когда «готово» | `.claude/agents/`, `.claude/commands/`, `gate.py`/`accept.py` + hooks §5–§6 |

Правило то же, что в v2: факт живёт ровно в одном слое. Новое: слой enforcement — это в
первую очередь **два скрипта** (`gate.py` — «зелено ли», `accept.py` — «можно ли принять»),
и только во вторую — хуки-эргономика.

Машиночитаемого индекса **нет** (решение зафиксировано): blast-radius вопросы отвечает
grep/агент по спекам и коду; индекс добавляется потом по принципу earn-its-place, если
реальная боль это докажет.

**Размещение commands vs skills** (решение зафиксировано): хотя рантайм Claude Code слил
команды и скиллы в один реестр, директории НЕ сливаем — `.claude/skills/` = слой знания
(авто-инвокация по description уместна), `.claude/commands/` = слой оркестрации (только
явный запуск человеком). Это A1/C4, материализованные в файловой системе: перенос команд
в каталог скиллов открыл бы авто-подгрузку процессных документов в контекст role-агентов
(C1-утечка наизнанку) и сломал бы каталожную машинерию §7 (инвентарь, coverage-суррогат).

**Target-приложение живёт В ЭТОМ репозитории** (решение зафиксировано, T01 finding 6):
`src/` + `tests/` + `specs/<context>/` — target; `.claude/` + `tasks/` + дизайн-доки — мета.
Это не удобство, а следствие двух механизмов: S9 требует веток и «main всегда зелёный» у
*продуктового* дерева, а self-integrity `gate.py` (E-02) сверяет гейт с git HEAD того же
репозитория, где идёт работа — git-ignored дерево (модель v2 `examples/generated/`) не даёт
ни того, ни другого. Один репозиторий = один продукт; v2-правило «target никогда не
коммитится» умерло вместе с манифестом. Извлечение workflow в плагин для отдельных
продуктовых репозиториев — после WP7 (упаковка и так отложена).

## §2. Хранилище спек: живая спека + дельты (brownfield-first)

Главная ошибка Spec Kit, которую не повторяем: спеки как одноразовые пофичевые артефакты,
которые не накапливаются в документацию системы. Форма — как у OpenSpec (propose → apply →
archive-merge), она же — наш F1 + `/apply-delta`, пересаженные на Markdown. **Единица хранения
тоже его:** каноническая спека — это НЕ один файл на контекст, а набор небольших файлов
**по capability**; иначе на зрелом контексте merge дельты упирается в LLM-правку
тысячестрочного документа (нарезка — главная митигация риска §12):

```
specs/
  <context>/                      # bounded context = ПАПКА (граница владения; зеркалит субпакет кода
    │                             #   в модели A — это не про микросервисы, а про локальность изменений)
    overview.md                   # карта контекста: зачем он, список capabilities (одной строкой каждая),
    │                             #   сквозные инварианты и доменные понятия, интеграции с соседями
    <capability>.md               # ЖИВАЯ спека одной capability, 50–300 строк (компаундится)
    changes/
      NNN-<slug>/                 # одно изменение = одна дельта-спека (живёт на СВОЕЙ ветке, см. ниже)
        change.md                 # Class / Context / Task / Interface sketch / AC / Verification
        criteria.md               # чеклист критериев (машинопроверяемый инвентарь, §3)
        verdict.md                # отчёт evaluator'а (пишется циклом, §6)
  use-cases/                      # исходники BA — verbatim, как раньше (вход upstream-стадий)
```

- **Capability-файл** — описание одной связной способности системы «как есть»: её операции,
  поведение, **инварианты с пометкой происхождения** (`(verified by: <test-id>)` /
  `(MANUAL)` — переносятся из принятых критериев, §5.4). Документ для человека и для
  ориентации агента (что уже существует — чтобы brownfield-агент не галлюцинировал требования
  на существующее поведение). Он НЕ схема и НЕ рендерится в код. Агенту под задачу собирается
  точечный контекст: `overview.md` + затронутые capability-файлы, не вся спека контекста.
- **Один change = одна ветка** (`change/<context>-NNN`, принцип S9). `/spec` создаёт ветку
  вместе с каталогом change'а; красные тесты, код и вердикт живут на ней; `main` получает
  только зелёные merge через `accept.py`. Это структурно снимает класс проблем «красные
  тесты одного change дедлочат гейт другого», «брошенный change — вечная мина», «два
  implementer'а в одном файле».
- **Жизненный цикл изменения:** `draft → in-progress → done → merged | abandoned`. Статус —
  это положение ветки и состояние `criteria.md`; отдельного поля статуса нет (наследие B4:
  никакого process state в спеке).
- **Принятие** (`/accept-change` → `accept.py`, §5.4): гейты пройдены → merge ветки в main,
  **критерии переносятся в capability-файлы как инварианты**, каталог `changes/NNN-<slug>/`
  **удаляется** (архив — это git-история + тег `change/<context>-NNN`; отдельной папки
  archive/ нет — она дублировала бы git и отравляла grep-blast-radius устаревшими
  снапшотами).
- **Greenfield — вырожденный случай:** первое изменение на пустом контексте (только скелет
  `overview.md`) — ровно F1. Формат первого change'а контекста — vertical slice, §9.
- **Adoption чужой legacy-кодбазы — вне охвата v3** (честная граница): house-style гейты
  на чужом коде красны навсегда. Режим `--adopt` (ratchet-baseline нарушений + генерация
  capability-скелетов с пометкой UNVERIFIED) — будущая работа, см. §12.

### 2.1 Правила нарезки спек

Два уровня, у каждого свой критерий:

**Уровень 1 — bounded context (папка).** Критерий v2 переживает дословно: *не меняются
вместе → разные контексты*. Признаки: свой доменный язык, свой кластер агрегатов, связь с
соседями через явные интерфейсы. Контекст зеркалит субпакет кода (модель A, монолит) — это
граница владения изменением, не деплоя.

**Уровень 2 — capability (файл).** Критерий — **cohesion по изменению**: capability = то,
что стейкхолдер назвал бы одной способностью системы и что дельты чаще всего меняют целиком
(«загрузка записей», «семантический поиск», «action items»). Обычно это 1 агрегат + его
операции, но не обязательно (у Meeting две capability: processing и search — оба про агрегат
Meeting). Правила:

- **Стартовая нарезка (greenfield):** одна capability на кластер пользовательских целей —
  на старте это часто 1–2 UC на файл. Нарезку предлагает `/spec` при первом изменении
  контекста, решает человек.
- **Что живёт в `overview.md`, а не в capability-файле:** сквозные доменные понятия
  (агрегаты/термины, которые видят несколько capabilities), инварианты уровня контекста
  (мульти-тенантность, квоты), карта интеграций. Правило: описание принадлежит capability,
  если меняется вместе с ней; иначе — вверх, в overview. Анти-anticipation литмус (дух B2):
  «вверх» — только если это видят ≥2 capability *сейчас*, а не «наверное понадобится».
- **Дельта, режущая несколько capabilities** — нормальна (quota касается upload и processing:
  merge в 2 файла). Сигнал тревоги — дельта, трогающая «почти все» файлы контекста: либо
  нарезка неверна, либо изменение надо резать. Дельта, режущая несколько **контекстов**,
  оформляется как парные change'и со ссылкой `Companion:` друг на друга; `accept.py` не
  принимает один без другого (полноценный кросс-контекстный change не вводим — earn-its-place).
- **Пороги пересмотра нарезки** (распространяются и на `overview.md`): файл вырос за
  ~300 строк → резать (для overview — выделять `glossary.md`/`invariants.md` как такие же
  канонические файлы под защитой); каждая вторая дельта трогает одну и ту же пару файлов →
  слить. Пере-нарезка — право `/spec` (интерактивная сессия с правами на канон): переносит
  текст между файлами И детерминированно переписывает `Affects:` во всех in-flight
  `changes/*/change.md`. Это ревьюируемый коммит, НЕ дельта-спека — поведение системы не
  меняется.

## §3. Формат спеки: секции, три глубины, чеклист критериев

### 3.1 `change.md` — секции

Одна обязательная секция — **Acceptance criteria**. Остальные добавляются по размеру задачи:

```markdown
# <context>/NNN — <короткое имя изменения>

Class: behavioral | bugfix | invisible    <!-- см. ниже; по умолчанию behavioral -->
Affects: <capability-файлы>               <!-- опционально; accept.py выведет сам, если строки нет -->
Companion: <context>/NNN                  <!-- только для парного кросс-контекстного изменения -->

## Context            <!-- зачем: 1–3 абзаца; ссылки на UC/capability-файлы; ТОЛЬКО для M/L -->
## Task               <!-- что сделать: своими словами; для S может быть всей спекой -->
## Out of scope       <!-- явно НЕ делаем (защита от расползания); опционально -->
## Interface sketch   <!-- M/L: имена модулей/классов + ctor-зависимости, которые тесты и код
                           ОБЯЗАНЫ разделять; контракт цикла, меняется только протоколом §6.
                           Пишется в /spec (агент предлагает, человек утверждает) -->
## Design notes       <!-- ТОЛЬКО L: выбор подхода, договорённости. NON-BINDING: разошлось
                           с кодом — прав код; evaluator при вердикте эту секцию игнорирует -->
## Acceptance criteria  <!-- ОБЯЗАТЕЛЬНАЯ. Наблюдаемое поведение работающей системы -->
## Verification       <!-- как прогнать доказательство: команды, сценарий e2e-проверки,
                           И подготовка окружения для live-прогона (seed-данные, docker,
                           токены) — без неё live-доказательство критерия НЕ требуется -->
```

**Три класса изменения** (лечит «нет полосы для не-поведенческих работ»):

- **behavioral** (дефолт) — новое/изменённое/удаляемое поведение; AC — наблюдаемое поведение.
  Removal-вкус (`REMOVED`): change явно перечисляет отменяемое поведение; test-author этого
  change'а **владеет удалением/правкой устаревших тестов** (D3 не ломается — он по-прежнему
  не автор кода), `accept.py` делает orphan sweep (§5.4).
- **bugfix** — код разошёлся с УЖЕ записанным инвариантом capability-файла; AC = ссылка на
  этот инвариант + регрессионный тест; merge в спеку обычно пуст (спека была права).
- **invisible** — рефакторинг, апгрейд зависимостей, перфоманс: поведение не меняется.
  AC = «поведение не изменилось», доказательство детерминированное: полный gate зелёный +
  diff OpenAPI-схемы до/после пуст (+ перф-метрика, если заявлена). Это узаконенное
  исключение из S3.

Правила формулировки критериев:
- Критерий — **наблюдаемое поведение работающей системы**, не свойство кода
  («`POST /meetings` с файлом >25 MiB возвращает 413 с кодом `request_too_large`»,
  НЕ «middleware настроен корректно»). Это A4, встроенный в формат.
- Given/When/Then приветствуется, но не обязателен — это проза для человека, не DSL.
- Секция Verification замыкает спеку: спека, у которой нет ответа на «как доказать, что
  готово», не принимается в работу (гейт в `/spec`, §6).

### 3.2 Три глубины — лекарство от церемонии фиксированного веса

Жалоба №1 на Spec Kit/Kiro — 16 критериев на мелкий баг, 1300 строк на отображение даты.
Правило: **если diff описывается одним предложением — хватит S.**

| Глубина | Секции | Когда |
|---|---|---|
| **S** | Task + Acceptance criteria (1–3 шт.) | багфикс, мелкое поведение |
| **M** | + Context, Out of scope, Interface sketch, Verification | типичная фича |
| **L** | + Design notes | новый контекст, новая интеграция, архитектурное изменение |

Глубину выбирает автор спеки; `/spec` предлагает, человек решает. Никакая секция, кроме
Acceptance criteria, не является обязательной — это защита от воспроизводства
overfitting-болезни «обязательными секциями вместо обязательных полей». Для S-глубины
работает **fast-lane** (§6): evaluator ограничивается `gate.py --criteria` без live-прогона.

### 3.3 `criteria.md` — чеклист, который можно только прощёлкивать

Сильнейший механизм из harness-практики Anthropic: инвентарь критериев, где агенты могут
переключать статус, но не могут переформулировать или удалить пункт. Это даёт главное, что
покупал манифест (ни один сценарий не выпадет молча), почти без церемонии.

```markdown
# Criteria — meetings/003-upload-recording
- [ ] AC-1: POST /meetings с валидным audio-файлом возвращает 201 и id митинга
- [ ] AC-2: превышение месячной квоты тарифа возвращает 402 с кодом quota_exceeded
- [x] AC-3: при падении записи в БД загруженный blob удаляется (компенсация), ответ 5xx
- [m] AC-4: файл >25 MiB отклоняется 413 ДО чтения тела целиком
```

- **Три состояния:** `[ ]` (не доказан) · `[x]` (доказан машинно) · `[m]` (принят человеком
  вручную — для критериев, которые ни тест, ни live-прогон покрыть не могут; ставит ТОЛЬКО
  человек, причина фиксируется в verdict.md).
- `[ ]`↔`[x]` переключает **только evaluator, в обе стороны** (нашёл регрессию на втором
  проходе — обязан разфлипнуть; храповик «только вперёд» запрещён). Роль-привязка —
  детерминированная, через `disallowedTools` (§5.2), не проза.
- **Каждый `[x]` машинно обеспечен:** тест несёт маркер критерия
  (`@pytest.mark.ac("AC-2")` — конвенция из `testing-unit`), а `gate.py --criteria` сверяет:
  на каждый `[x]` существует помеченный **passed**-тест в junit-отчёте текущего прогона.
  Флип без обеспечения — RED на гейте, независимо от того, кто и как его поставил.
- Текст пункта после старта работ (= коммита красных тестов) **неизменяем**: правка формы
  ловится criteria-guard'ом (эргономика, §5.2), а подмена в обход — integrity-сверкой
  `gate.py` (§5.1). Добавить/изменить критерий может только человек через `/spec`-сессию
  с пересбросом цикла.
- **Lint критериев** (детерминированный, в `/spec`-гейте): пункт обязан называть наблюдаемый
  артефакт (HTTP-код, поле ответа, состояние после запуска); слова-маркеры расплывчатости
  («корректно», «правильно», «works», «как ожидается») — отказ. Расплывчатый критерий не
  проходит в работу — это громкая деградация вместо тихой (наследник loud degradation v2).

## §4. Роли: три агента + человек (D1 сохраняется)

Ролей мало, различаются контекстом, не форком промпта. Scaffolder/implementer-пара v2
уходит; файловая граница собственности сдвигается с «declarative vs body» на **«tests vs
src»** — это новая D4. Каждый агент — отдельное определение в `.claude/agents/` с
**`disallowedTools` во frontmatter** — это и есть механизм роль-привязки (проверен по докам:
PreToolUse-hook НЕ знает, какой сабагент его вызвал, а frontmatter-ограничения знает сам
диспатчер; см. `notes/15` F-2).

| Роль | Кто | Делает | Не может (enforcement) |
|---|---|---|---|
| **spec-author** | человек + главная сессия (`/spec`) | интервью → `change.md` + `criteria.md` + Interface sketch; нарезка/пере-нарезка capabilities | код и тесты: не пишет (интерактивная сессия под наблюдением человека — здесь достаточно совета) |
| **test-author** | сабагент, отдельный контекст | из спеки + Interface sketch пишет **красные** тесты с `ac`-маркерами; при removal-классе — удаляет/правит устаревшие тесты; подтверждает красноту скриптом; коммитит | `disallowedTools`: Edit/Write по `src/**`; criteria.md/verdict.md |
| **implementer** | сабагент | код до зелёного `gate.py`; владеет и Alembic-ревизией (правила — в `infra-persistence`); упёрся в Interface sketch → **contract-change protocol** (§6), не молчаливый обход | `disallowedTools`: Edit/Write по `tests/**`, `specs/**`, `.claude/**`, `pyproject.toml`; SubagentStop не выпускает при красном gate |
| **evaluator** | сабагент, **свежий контекст** | прогоняет `gate.py` полностью, live-проверяет критерии, у которых Verification обеспечил окружение; флипает `[ ]`↔`[x]` с doказательством; пишет `verdict.md` (+ отчёт о src-diff вне области change'а — громко, не запрет) | `disallowedTools`: Edit/Write по `src/**`, `tests/**`; писать может только verdict.md и флипы criteria.md |

Анти-паттерны, которые эта раскладка закрывает (оба — самые задокументированные провалы
агентских циклов): **self-evaluation bias** (работник хвалит свою работу → evaluator всегда
в свежем контексте и не автор кода) и **collusion** (тест и код пишутся из одного понимания
→ test-author пишет тесты из спеки ДО кода, implementer тесты трогать не может — наш D3,
теперь и официальный гайдлайн Anthropic/OpenAI). Третий шов — «кто владеет именами» —
закрывает Interface sketch: тесты и код пишутся против ОДНОГО опубликованного контракта,
а не против изобретений test-author'а (урок v2/F-020).

Уточнение к test-author в brownfield: читать существующий код (интерфейсы, фикстуры,
существующие тесты) — можно и нужно; запрет распространяется на запись в `src/**`.

Honesty-правило для evaluator (из ревью, O-02): live-прогон критерия обязателен только
там, где секция Verification обеспечила окружение (seed-скрипт, docker-compose, токены);
для остальных критериев доказательство = помеченный `ac`-тест, и verdict.md явно говорит,
какой способ применён к каждому AC. Молчаливая подмена live-прогона цитатой pytest
запрещена — но это правило honesty, страхуемое тем, что `[x]` в любом случае требует
junit-обеспечения (§3.3).

## §5. Enforcement: gate как якорь доверия

Иерархия — от совета к невозможности. **Инверсия после ревью (S8):** prevention-хуки —
эргономика (быстрый отказ с объяснением); **якорь доверия — `gate.py`, который не верит
файловой системе на слово**, а сверяет её с git-baseline. Обход хука не помогает агенту:
результат обхода обесценивается на гейте.

1. **Скиллы** (проза) — house style, «как принято». Нарушение возможно → страхуется ниже.
2. **Тулчейн** — mypy / ruff / pytest; конфиг живёт **внутри `gate.py`** (одна точка правды;
   `conventions` его цитирует, не наоборот — иначе циклическая зависимость WP3↔WP4).
3. **`gate.py`** — детерминированная сверка результата (5.1).
4. **`accept.py`** — детерминированные предусловия принятия (5.4). Гейты принятия — скрипт,
   НЕ проза команды (S4, применённый к самому воркфлоу).

### 5.1 `gate.py` — одна точка правды о «зелёном»

Stdlib-only скрипт (как валидатор v2). Печатает машиночитаемый вердикт (`GREEN` / список
красного) + junit-xml + git SHA прогона. Используется всеми: SubagentStop implementer'а,
evaluator, `accept.py`, человек. **Исчерпывающий инвентарь проверок** (каждая наследует
конкретную оплаченную находку v2/ревью — не сокращать молча):

- Тулчейн: `mypy src tests` · `ruff check` · `ruff format --check` (select включает `B006`,
  `B904`) · `pytest` **с пиновкой конфига** (`--override-ini=addopts=`, фиксированный
  rootdir) — глушение через conftest/pyproject не работает (E-05).
- Grep-гейты: `# type: ignore` на content-модулях (F-023) · `from __future__ import
  annotations` (N-03) · `# noqa: F401` · **`raise NotImplementedError` в `src/**`** —
  заглушка в непокрытой ветке зелёная для mypy, но это A4-класс (V-04).
- Construct-smoke: `create_app()` + `app.openapi()` (A4) · metadata-import smoke для
  таблиц (F-012).
- Docker-tier (когда Docker доступен): testcontainers + **`alembic upgrade head`**; иначе
  громкая пометка `DOCKER SKIPPED` в вердикте — не молчаливый пропуск.
- `--criteria`: каждый `[x]` в criteria.md обеспечен существующим **passed** `ac`-тестом
  в junit текущего прогона; `[m]` — только с записью в verdict.md (E-07/V-10/O-11).
- **Integrity против baseline** (baseline = коммит красных тестов на ветке change'а):
  - diff защищённых деревьев: `criteria.md` (только легальные флипы состояния),
    hash `change.md`, `.claude/tools/**`, `.claude/hooks/**`, `.claude/settings.json`,
    `pyproject.toml` — любое расхождение = RED (E-01/E-02/E-12);
  - **инвентарь тестов**: собранные pytest node-id ⊇ инвентарь baseline; пропавший,
    skipped или xfail-нутый тест из baseline = RED (закрывает удаление/deselect/
    conftest-глушение разом, E-05); легальное удаление тестов существует только в
    removal-change и перечислено в его change.md. *Единственное исключение* (design
    ruling, T04 finding 2): baseline-тест из интеграционной директории, скипнутый при
    том, что **собственная проба гейта** установила отсутствие Docker-демона, — не RED,
    а строка в громком `DOCKER SKIPPED`-блоке вердикта; ключ исключения — проба гейта
    (факт среды), никогда не строка skip-reason, которую агент мог бы имитировать;
    при живом демоне исключения нет;
  - self-integrity: hash самого `gate.py` и тулчейн-конфига против git HEAD (E-02).

### 5.2 Роль-привязка и хуки-эргономика

- **Роль-привязка = `disallowedTools` во frontmatter агентов** (§4) — механизм подтверждён
  по докам; форжимых маркер-файлов нет (E-04 снята). Per-dispatch тюнинг тулов не
  поддерживается — при нужде заводится отдельное определение агента.
- **PreToolUse-хуки** остаются как быстрый отказ с объяснением (агент понимает «почему
  нельзя» до, а не после):
  - `criteria-guard`: на Edit — сравнение old/new (только флип состояния в начале строки);
    на **Write — чтение файла с диска и построчный diff** (поля old/new у Write нет, F-1);
    создание criteria.md легально только до существования baseline-коммита;
  - `bash-guard` (best-effort): PreToolUse на Bash, deny-паттерны записи в защищённые пути;
  - скрипты хуков каноникализуют пути (`realpath` + `casefold` — APFS регистронезависима,
    symlink/`..`-обходы; E-10).
- Прорыв любого хука не фатален: его результат ловит integrity-сверка 5.1.

### 5.3 Stop-гейты и эскалация

- **SubagentStop на implementer:** `{"decision": "block"}` пока `gate.py` красный; скрипт
  уважает `stop_hook_active` и системный потолок блокировок. Достигнут потолок итераций →
  **сам hook** (не агент) пишет файл `changes/NNN-<slug>/ESCALATE` с причиной — эскалация
  материальна, не строчка в эфемерном отчёте (E-08).
- **Stop на главной сессии в `/implement`:** ход не завершён, пока в criteria.md есть `[ ]`
  ИЛИ нет verdict.md ИЛИ есть ESCALATE-файл — последний случай завершается только явным
  обращением к человеку.
- `accept.py` при наличии ESCALATE — deny; снять файл может только человек.

### 5.4 `accept.py` — предусловия принятия (скрипт, не проза)

Гейты (все детерминированные):
1. criteria.md: все пункты `[x]` или `[m]`; каждый `[x]` обеспечен junit'ом. Обеспечение
   `accept.py` **сам перепрогоняет `gate.py --criteria` на HEAD ветки** — не доверяет
   git-ignored `.gate/verdict.json` (S8: артефакту на слово не верим); перепрогон
   детерминированного гейта ≠ пересчёт дорогого evaluator-цикла, от которого страхует L-04.
   SHA вердикта == HEAD ветки (иначе evaluator-пересчёт обязателен только если diff
   `verdict-SHA..HEAD` пересекается с файлами change'а — L-04; verdict-метаданные-коммиты
   из пересечения исключены, иначе нормальная последовательность evaluator→verdict вечно
   требовала бы пересчёта).
2. `gate.py` GREEN на ветке; ESCALATE отсутствует; `Companion:` (если есть) принят или
   принимается этим же прогоном.
3. **Affects-пересечение**: `Affects` принимаемого change'а ∩ `Affects` всех in-flight
   changes → пересёкшиеся флагуются человеку на пере-ревью их критериев (L-03).
4. **Merge-fidelity pre-check**: каждый AC дельты находим (grep-класс) в diff'e вливания
   в capability-файлы — штамп человека ложится на проверенный diff (L-11).
5. **Spec-lint**: висячие ссылки между spec-файлами, дубли capability, файлы >300 строк,
   capability без строки в overview.md; плюс LLM-проход «утверждения корпуса, противоречащие
   дельте» — вывод в ревью-diff человеку (L-07/O-13).
6. **Orphan sweep** (для removal): упомянутое как удалённое поведение не осталось ни в
   spec-тексте, ни мёртвыми символами в src (grep-класс).

Действия после «да» человека: критерии → инварианты capability-файлов с пометкой
`(verified by: <test-id>)` / `(MANUAL)`; merge ветки в main; тег; удаление каталога
change'а. **Распределение инвариантов по нескольким capability-файлам (multi-target
`Affects`) — семантический акт, не детерминированный:** он принадлежит `/accept-change`
(T10 — LLM предлагает, какой инвариант в какой файл, человек утверждает) ПЕРЕД
`accept.py --execute`; сам `accept.py` при multi-target только флагует распределение, не
сваливает всё в первый файл. Single-target (обычный/greenfield случай) `accept.py` кладёт
детерминированно. `gate.py` впредь grep'ом проверяет, что тесты, на которые ссылаются
инварианты, существуют (L-06). Запись в канонические spec-файлы разрешена только этому
скрипту и `/spec`-сессии (spec-guard — эргономика, integrity — сверка).

### 5.5 Дрейф и hotfix-lane

Хотфикс мимо воркфлоу легален (прод горит), но не молчалив:
- **retro-delta**: `/spec --retro` — change постфактум (Class: bugfix/behavioral), суть
  хотфикса вливается в capability-файл обычным `/accept-change`;
- **drift-check**: `accept.py` и `/orient` сверяют capability-файлы с наблюдаемой
  поверхностью (OpenAPI-роуты ⊆ описанные операции и наоборот) и репортят рассинхрон;
  список src-коммитов main, не привязанных к change-тегам, выводится там же (L-02/O-08).

## §6. Цикл: команды и протокол итераций

Команды: `/spec` → `/implement` → `/accept-change`, плюс `/abandon`. Охват — «ядро»;
upstream-стадии v2 переносятся потом.

### `/spec [<context>] [<описание>]  [--retro]`
Интерактивная. Интервью с человеком (AskUserQuestion по неоднозначностям — аналог
`/clarify` у Spec Kit и «interview → SPEC.md» у Anthropic): читает `overview.md` + затронутые
capability-файлы (при первом изменении контекста — предлагает нарезку по §2.1), задаёт
вопросы, предлагает класс и глубину S/M/L, для M/L предлагает Interface sketch, пишет
`change.md` + `criteria.md`. Аллоцирует `NNN = max(существующих ∪ тегов) + 1` в контексте;
id everywhere — `<context>/NNN`. Создаёт ветку `change/<context>-NNN`. Гейт на выходе:
criteria-lint (§3.3) + Verification отвечает «как доказать» (для live-критериев — чем
обеспечено окружение). Спека — на языке диалога с пользователем (русский); это вход для
человека, не для машины.

### `/implement <context>/NNN`
Цикл на ветке change'а. Шаги:

1. **test-author** (сабагент): тесты из criteria + Interface sketch (каждому AC — минимум
   один тест с маркером `@pytest.mark.ac("AC-n")`, где это физически возможно; невозможное —
   кандидат в `[m]`, явно в отчёте); при removal-классе — правит/удаляет устаревшие тесты
   (перечисляя их, — попадут в baseline-инвентарь как легально удалённые); **красноту
   подтверждает скрипт** (шаг runner'а, не совет: тест, зелёный до имплементации,
   подозрителен); **коммит красных тестов = baseline** для integrity-сверок 5.1.
2. **implementer** (сабагент): код до зелёного `gate.py`. Скиллы подгружаются
   авто-инвокацией (§7). Упёрся в Interface sketch (нужен третий dep, имя неудачно) —
   **contract-change protocol**: пишет CONTRACT-CHANGE в отчёт, цикл возвращается на шаг 1
   свежим test-author'ом, который правит тесты под уточнённый sketch (правку sketch'а
   утверждает человек, если change M/L — иначе главная сессия). Никаких молчаливых
   обходов (default-аргументы ради тестов). Внутренний потолок: 3 итерации на красный
   тест → ESCALATE (порог v2, он себя оправдал).
3. **evaluator** (свежий сабагент): полный `gate.py` (+ `--criteria`) + live-прогон
   критериев, обеспеченных Verification-окружением → флипы `[ ]`↔`[x]` → `verdict.md`
   (по каждому AC: PASS/FAIL/MANUAL-candidate + способ доказательства + git SHA; плюс
   src-diff вне области change'а — громко). **Fast-lane для S-глубины:** evaluator =
   `gate.py --criteria`, без live-прогона.
4. **Адверсариальный проход** — обязателен для M/L и для первого change'а каждой
   capability (наследник §9-механики v2: свежий агент прогоняет рецепты силы ассертов
   из `testing-unit` по diff'у тестов, вердикт — секция в verdict.md; `accept.py`
   проверяет её наличие по классу change'а). Для S — опция `--adversarial`.
5. **Ветвление:** все AC зелёные → готово, человеку на `/accept-change`. Есть FAIL →
   verdict.md уходит новому implementer-диспатчу (шаг 2) с конкретикой провала. Потолок
   полного цикла: 3 прохода → ESCALATE-файл → человек.

Одновременно в `/implement` — не более одного change'а на контекст (простое правило вместо
блокировок; пересечения остальных in-flight ловит Affects-гейт accept'а).

### `/accept-change <context>/NNN`
Обёртка над `accept.py` (§5.4): гейты → ревью diff'а человеком → merge в main + тег +
удаление каталога change'а.

### `/abandon <context>/NNN`
Брошенный change: ветка удаляется (красные тесты никогда не попадали в main — S9 делает
это тривиальным), заметка с причиной — в git-тег `abandoned/<context>-NNN`.

## §7. Скиллы: ревизия + слияние 44 → ~13

Что делает ревизия (один проход, решение зафиксировано):
1. **Вычистить манифест-связку:** упоминания kind→skill диспатча, манифест-слайсов,
   «validator/scaffolder/runner» — всё это отсылки к оркестрации v2 (нарушение C1 задним
   числом). Human-onboarding тест C3 — критерий чистки.
2. **Слить группы** до гранулярности, которую агент выбирает сам, с frontmatter-полями
   **`description` + `when_to_use`** для авто-подгрузки (поля `when` не существует — F-6;
   лимит 1536 символов на скилл в листинге; авто-инвокация работает и в сабагентах):

| Новый скилл | Поглощает | Примечание |
|---|---|---|
| `conventions` | себя (урезается) | пути/нейминг/store-profiles/substrate остаются; kind→skill реестр — удаляется; тулчейн-команды ЦИТИРУЮТ gate.py |

   (само-отчётный diff-протокол недостаточен, V-07):
   - **до слияния** составляется машинный инвентарь «оплаченных строк»: по каждому
     закрытому F/N-номеру — grep-паттерн его фикса в текущем каталоге (F-013 root-conftest,
     F-015 третий try/except, F-016 `*_best_effort` опционален, F-018 fake-копии+updated-лог,
     F-019 конкретный сервис не фейкается, F-004 workspace_id-стемпинг, N-01 импорт с
     непосредственного родителя, N-02 getattr на FastAPI-внутренностях, two-sub-template
     идиомы, запрет ORM, offset-vs-cursor **взаимоисключение** — «выбери одно, никогда оба»
     (`domain-filter`; НЕ «запрет cursor» — cursor это санкционированная альтернатива, T07
     finding 1 поймал эту ошибку формулировки), …);
   - `test-principles` переписывается **до** слияния и зелёнит этот инвентарь против
     нового каталога — сторож не переписывается той же рукой, что сторожит;
   - по каждому Hard stop сливаемого скилла — явное решение: **получает grep-гейт в
     gate.py или сознательно понижается до совета** (litmus S4); список решений — артефакт
     ревизии (O-12).
4. **Harvest agent prompts** (V-08): правила, живущие в удаляемых `.claude/agents/*.md`,
   получают новый дом или явную пометку «умерло, потому что…». Известные: env_prefix —
   продукт, не контекст (N-04 → `infra-integration`); ConflictError при первом insert на
   unique (architect r9 → `infra-persistence`); flat-vs-review-tail дисциплина
   (implementer v2 → протокол §6).
5. **Суррогат §16-гейта покрытия** (C5, V-03): evaluator/gate сверяет пути diff'а
   (`domain/`, `application/`, `infrastructure/<tech>/`, `restapi/`, `tests/`) со списком
   скиллов, которые агенты отчитали загруженными: пустое пересечение на слое —
   loud-warning в verdict; **новый `infrastructure/<tech>`-подкаталог без скилла — STOP**
   на `meta-skill-author` + человек (presence-gap, как в v2).

Четырёхсекционный формат (`When to use / Templates / Rules / Hard stops`) сохраняется —
он не зависит от манифеста и хорошо работает на двух читателей.

## §9. Примеры прохода (S-случай и L-случай)

**S-случай** — «UC-16: участник может закрыть action item» (реальная дельта из dry-run v2):

1. `/spec meetings "закрытие action item по UC-16"` → интервью (идемпотентность? кто вправе?)
   → ветка `change/meetings-004`, `specs/meetings/changes/004-complete-action-item/change.md`
   (Class: behavioral, глубина S) + `criteria.md`: AC-1 `POST /action-items/{id}/complete`
   от участника воркспейса → 200, статус DONE; AC-2 повторный вызов того же `POST` → 200,
   статус остаётся DONE (идемпотентность); AC-3 чужой item → 404 без утечки существования.
2. `/implement meetings/004`: test-author — 3 `ac`-помеченных теста → краснота подтверждена
   скриптом → baseline-коммит; implementer — enum grows DONE, протокол grows
   `get_by_id/update`, хендлер, роут (скиллы `domain-model`/`application`/`restapi`
   подгрузились по description); gate GREEN; evaluator fast-lane — `gate.py --criteria`,
   3/3 AC `[x]` с junit-обеспечением, verdict с SHA.
3. `/accept-change meetings/004` → accept.py: гейты + merge-fidelity + spec-lint → человек
   одобрил diff в `specs/meetings/action-items.md` (~15 строк: операция + инвариант
   идемпотентности `(verified by: ...)`) → merge в main, тег, каталог удалён.

**L-случай** — «новый контекст billing: тарифы + Redis-кэш лимитов» (проверка формата на
самом тяжёлом входе; правило **vertical slice**): первый change нового контекста НЕ режется
на «bootstrap» / «DI» / «таблицы» (у них нет наблюдаемого поведения — S1/S3 запрещают такие
AC), а оформляется как один L-change с ОДНИМ сквозным наблюдаемым AC («`GET /billing/plan`
авторизованного пользователя возвращает его тариф и лимиты») плюс весь substrate по дороге:
bootstrap владеет implementer через скиллы `architecture`/`restapi`/`infra-*`, Alembic-ревизию
пишет implementer, Docker-tier гоняет `upgrade head`. Interface sketch обязателен; жить он
будет дольше 30 минут — и это легально для vertical slice (риск §12.5 говорит о
раздутых S/M, не об этом узаконенном случае).

Сравнить с тем же изменением в v2 (architect-делта → validate → re-scaffold → drift-trigger
→ implementer → verify): цепочка v3 короче на два механизма (валидатор, планировщик) при
том же уровне доказательности. Это и есть проверяемое обещание v3.

## §11. S-серия принципов (замена B-серии; кандидаты в PRINCIPLES.md при WP1)

**S1 · Спека описывает поведение, не устройство.** *Trigger:* тянет записать в спеку имя
класса, путь, тип колонки. *Litmus:* это проверяемо снаружи работающей системы? Нет →
это Design notes (non-binding) или решение implementer'а. *Исключение с владельцем:*
Interface sketch — binding-контракт цикла, меняемый только протоколом §6. *Why:* устройство —
производная; но у имён, которые разделяют test-author и implementer, обязан быть один хозяин.

**S2 · Один формат, три глубины; ceremony по размеру diff'а.** *Trigger:* хочется сделать
секцию обязательной. *Litmus:* нужна ли она S-спеке из одного предложения? Нет → опциональна.
*Why:* обязательные секции — это обязательные поля v2 в новой одежде.

**S3 · Критерий — наблюдаемое поведение; чеклист append-only для агентов.** *Trigger:*
критерий формулируется про код («используется паттерн X») или агент хочет уточнить пункт.
*Do:* переформулировать через запуск системы; правка текста — только человеком; flip только
с junit-обеспечением. *Узаконенные исключения:* класс invisible (AC = «поведение не
изменилось», доказательство — gate + OpenAPI-diff) и `[m]` (принято человеком, с причиной).
*Why:* A4 + «ни один сценарий не выпадает молча» — то, ради чего жил манифест.

**S4 · Must-hold правило живёт в гейте, не в прозе.** *Trigger:* в скилл/спеку/команду
пишется «никогда не делай X» или «Y делает только Z». *Litmus:* что физически произойдёт,
когда агент всё-таки сделает X? Если ответ «ничего» — правило не существует; добавь
grep-гейт/integrity-сверку/disallowedTools или сознательно понизь до совета. *Why:* провал 2
обоих прошлых поколений; на дизайн-ревью этот литмус завалил четыре правила самого v3.

**S5 · Вердикт выносит не автор.** *Trigger:* агент, писавший код, отчитывается «критерии
выполнены». *Do:* вердикт валиден только из свежего контекста evaluator'а + `gate.py
--criteria`; сила тестов для M/L проверяется адверсариальным проходом. *Why:*
self-evaluation bias — самый задокументированный провал агентских циклов.

**S6 · Дельта вливается, спека компаундится.** *Trigger:* change принят. *Do:* критерии →
инварианты capability-файлов (с provenance-пометкой), merge — немедленно, ревьюированно;
каталог change'а удаляется — история только в git. *Why:* одноразовые спеки — главное
архитектурное сожаление Spec Kit; вторая копия истории отравляет grep.

**S7 · Capability режется по cohesion-of-change.** *Trigger:* решается, где живёт кусок
спеки, или файл растёт (включая overview.md). *Litmus:* меняется вместе с этой способностью →
в её файл; видят ≥2 capability сейчас → в overview; файл >~300 строк → резать; каждая вторая
дельта трогает одну и ту же пару файлов → слить. *Why:* локальность merge — то, что делает
LLM-вливание дельты ревьюируемым; монолитная спека контекста его убивает. `§2.1`

**S8 · Хук — эргономика; доверие — post-hoc сверка с baseline.** *Trigger:* хочется
защитить инвариант prevention-хуком и успокоиться. *Litmus:* что увидит `gate.py`, если
агент обойдёт хук через Bash/Write/conftest/правку самого гейта? Если «ничего» — инвариант
не защищён: добавь его в integrity-инвентарь §5.1 (diff защищённых деревьев, инвентарь
тестов, junit-кросс-чек, self-hash). *Why:* prevention дыряв по построению; обесценивание
результата обхода — нет. `notes/15, тема 1`

**S9 · Один change = одна ветка; main всегда зелёный.** *Trigger:* красные тесты просятся
в общее дерево, или два change'а хотят работать одновременно. *Do:* красные тесты, код и
вердикт живут на ветке change'а; main получает только зелёные merge через accept.py;
брошенный change = удалённая ветка. *Why:* закоммиченные красные тесты одного change'а
дедлочат гейт всех остальных; поток изменений нуждается в детерминизме не меньше, чем
один change. `notes/15, тема 2`

## §12. Риски и открытые вопросы

1. **Окружение evaluator'а — самая недооценённая стройка** (O-02). Live-доказательство
   реальных бизнес-критериев (квоты, биллинг, внешние API) требует seed/секретов/денег.
   Митигация: honesty-правило §4 (live только там, где Verification обеспечил окружение) +
   named-внимание в WP5. Остаточный риск: доля `[m]` и «доказано только тестом» растёт со
   зрелостью приложения — мерить на WP7.
2. **Merge дельты в каноническую спеку — LLM-шаг с человеком-ревьюером.** Страховки: merge
   локален по построению (capability-файл 50–300 строк, §2.1/S7) + маленькие дельты (S2) +
   merge-fidelity pre-check + spec-lint (§5.4). Если конкретный файл гниёт — пере-нарезка
   по порогам S7, а не ужесточение формата.
3. **Стоимость цикла и пропускная способность человека** (L-11/O-08). Три сабагента + два
   человеческих тучпоинта на change. Митигации: fast-lane S, merge-fidelity pre-check
   (штамп над проверенным diff'ом), retro-delta как легальный клапан вместо тихого обхода.
   Батч-accept — отложен до замеров WP7. Красная линия: если после WP7 автор сам обходит
   воркфлоу на мелочах — чинить ценой, а не дисциплиной.
4. **Blast-radius без графа.** Отвечаем grep'ом и чтением spec-файлов; drift-check §5.5
   частично страхует. На большой системе может заболеть → тонкий индекс (сознательно
   отложено, B1/earn-its-place).
5. **Слишком крупные S/M-change'и.** Implementer одного change'а живёт >30 мин вне
   vertical-slice случая — сигнал резать спеку. Vertical slice (§9-L) — узаконенное
   исключение.
6. **Adoption legacy-кодбазы — вне охвата** (L-08, честная граница v3). Будущее: `--adopt`
   (ratchet-baseline нарушений + capability-скелеты UNVERIFIED).
7. **Upstream-стадии** (PDF → use-cases → вопросы BA) — вне охвата ядра; analyst-механика v2
   концептуально совместима (её выход станет `/spec`-входом), перенос — после WP7.
