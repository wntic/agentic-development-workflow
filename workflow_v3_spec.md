# Workflow v3 — спека в Markdown, детерминизм в гейтах

Дизайн-документ третьей итерации воркфлоу. Предшественник — `codegen_workflow_spec.md`
(v2: YAML-манифест + валидатор + scaffolder/implementer по DAG). Этот документ — источник
правды для v3; он написан как ТЗ, по которому воркфлоу реализуется без дополнительного
контекста. Статус v2: доказан end-to-end (см. `notes/pipeline_dryrun_feedback.md`),
заархивирован в истории `main`; v3 строится в этой ветке.

---

## §0. Мотивация: два провала и их настоящие причины

v1 (генератор) и v2 (манифест + агенты) споткнулись об одни и те же два камня:

**Провал 1 — схема спеки переобучалась под референсное приложение.** Каждое новое приложение
требовало расширения схемы; три раунда аудита скиллов (~80 находок «заморозили фичу одного
приложения как универсальную») и 25 находок dry-run'а — это цена поддержки жёсткой схемы.
*Диагноз:* схема — неправильная **точка приложения строгости**. Строгий формат нужен там, где
проверяется результат, а не там, где описывается намерение. Индустрия пришла к тому же:
все выжившие инструменты (Spec Kit, Kiro, OpenSpec, SPEC.md-подход Anthropic, AGENTS.md у
OpenAI) используют секционированный свободный Markdown; жёсткие DSL живут только в рисёрче.

**Провал 2 — агенты нарушали правила, записанные в скиллах.** *Диагноз:* правило в прозе —
совет, а не ограничение; у Spec Kit задокументирован идентичный случай (constitution.md
запрещал try/catch — агент писал их всё равно). Смена формата спеки это НЕ лечит. Лечит
перенос каждого must-hold правила из прозы в **детерминированный гейт**: hook, который
блокирует действие до его выполнения; grep-гейт; тулчейн; Stop-гейт «нельзя завершить ход,
пока красное». v2 уже наполовину знал это (принцип A3 — «детерминизм живёт в верификации»);
v3 доводит до конца: детерминизм живёт в верификации **и в enforcement**, нигде больше.

Отсюда спинной хребет v3, в одну строку:

> **Спека — свободный Markdown для человека и ориентации агента. Критерии приёмки — чеклист,
> который агент может только прощёлкивать. Все must-hold правила — детерминированные гейты.
> Цикл: тесты → код → запуск → сверка с критериями → итерация.**

Что переживает из PRINCIPLES.md: A1 (слои не смешиваются — в новой формулировке §1), A3, A4,
C1–C7 (скиллы), D1 (мало ролей), D3 (anti-collusion), F1 (brownfield-first). Что уходит:
A2 и вся B-серия (манифест) — их заменяет S-серия (§11).

| **Знание** | как писать артефакт (house style) | `.claude/skills/` — после ревизии §7 |

## §2. Хранилище спек: живая спека + дельты (brownfield-first)

Главная ошибка Spec Kit, которую не повторяем: спеки как одноразовые пофичевые артефакты,
которые не накапливаются в документацию системы. Форма — как у OpenSpec (propose → apply →
archive-merge), она же — наш F1 + `/apply-delta`, пересаженные на Markdown:

```
specs/
  <context>/                      # bounded context (accounts, meetings, ...)
    spec.md                       # ЖИВАЯ каноническая спека контекста (компаундится)
    changes/
      NNN-<slug>/                 # одно изменение = одна дельта-спека
        change.md                 # Context / Task / Acceptance criteria / Verification
        criteria.md               # чеклист критериев (машинопроверяемый инвентарь, §3)
        verdict.md                # отчёт evaluator'а (пишется циклом, §6)
    archive/
      NNN-<slug>/                 # принятые изменения (после вливания в spec.md)
  use-cases/                      # исходники BA — verbatim, как раньше (вход upstream-стадий)
```

- **`spec.md`** — описание системы «как есть»: обзор контекста, доменные понятия и инварианты,
  операции (что система умеет), интеграции. Это документ для человека и для ориентации агента
  (что уже существует — чтобы brownfield-агент не галлюцинировал требования на существующее
  поведение). Он НЕ схема и НЕ рендерится в код.
- **Жизненный цикл изменения:** `draft → in-progress → done → merged`. Статус — это положение
  файлов (в `changes/` или `archive/`) + состояние `criteria.md`; отдельного поля статуса нет
  (наследие B4: никакого process state в спеке).
- **Принятие** (`/accept-change`, §6): все критерии зелёные + человек посмотрел → агент вливает
  суть дельты в `spec.md` (человек ревьюит diff), каталог переезжает в `archive/`.
- **Greenfield — вырожденный случай:** первое изменение на пустом `spec.md` (ровно F1).

## §3. Формат спеки: секции, три глубины, чеклист критериев

### 3.1 `change.md` — секции

Одна обязательная секция — **Acceptance criteria**. Остальные добавляются по размеру задачи:

```markdown
# NNN — <короткое имя изменения>

## Context            <!-- зачем: 1–3 абзаца; ссылки на UC/spec.md; ТОЛЬКО для M/L -->
## Task               <!-- что сделать: своими словами; для S может быть всей спекой -->
## Out of scope       <!-- явно НЕ делаем (защита от расползания); опционально -->
## Design notes       <!-- ТОЛЬКО L: имена файлов/интерфейсов, выбор подхода, договорённости -->
## Acceptance criteria  <!-- ОБЯЗАТЕЛЬНАЯ. Наблюдаемое поведение работающей системы -->
## Verification       <!-- как прогнать доказательство: команды, сценарий e2e-проверки -->
```

Правила формулировки критериев:
- Критерий — **наблюдаемое поведение работающей системы**, не свойство кода
  («`POST /meetings` с файлом >25 MiB возвращает 413 с кодом `request_too_large`»,
  НЕ «middleware настроен корректно»). Это A4, встроенный в формат.
- Given/When/Then приветствуется, но не обязателен — это проза для человека, не DSL.
- Секция Verification замыкает спеку: спека, у которой нет ответа на «как доказать, что
  готово», не принимается в работу (гейт в `/spec`, §6).

### 3.2 Три глубины — лекарство от церемонии фиксированного веса

Жалоба №1 на Spec Kit/Kiro — 16 критериев на мелкий баг, 1300 строк на отображение даты.
Правило: **если diff описывается одним предложением — хватит S.**

| Глубина | Секции | Когда |
|---|---|---|
| **S** | Task + Acceptance criteria (1–3 шт.) | багфикс, мелкое поведение |
| **M** | + Context, Out of scope, Verification | типичная фича |
| **L** | + Design notes | новый контекст, новая интеграция, архитектурное изменение |

Глубину выбирает автор спеки; `/spec` предлагает, человек решает. Никакая секция, кроме
Acceptance criteria, не является обязательной — это защита от воспроизводства
overfitting-болезни «обязательными секциями вместо обязательных полей».

### 3.3 `criteria.md` — чеклист, который можно только прощёлкивать

Сильнейший механизм из harness-практики Anthropic: инвентарь критериев, где агенты могут
переключать статус, но не могут переформулировать или удалить пункт. Это даёт главное, что
покупал манифест (ни один сценарий не выпадет молча), почти без церемонии.

```markdown
# Criteria — 003-upload-recording
- [ ] AC-1: POST /meetings с валидным audio-файлом возвращает 201 и id митинга
- [ ] AC-2: превышение месячной квоты тарифа возвращает 402 с кодом quota_exceeded
- [ ] AC-3: при падении записи в БД загруженный blob удаляется (компенсация), ответ 5xx
- [ ] AC-4: файл >25 MiB отклоняется 413 ДО чтения тела целиком
```

- `- [ ]` → `- [x]` переключает **только evaluator** (§4) и **только с доказательством**
  (имя зелёного теста или воспроизведённый сценарий на запущенном приложении, фиксируется
  в `verdict.md`).
- Текст пункта после старта работ **неизменяем для агентов** — enforcement детерминированный
  (hook, §5.2). Добавить/изменить критерий может только человек (или агент в интерактивной
  сессии `/spec` до старта работ).

## §4. Роли: три агента + человек (D1 сохраняется)

Ролей мало, различаются контекстом, не форком промпта. Scaffolder/implementer-пара v2
уходит (без манифеста нет детерминированного скаффолд-прохода); файловая граница
собственности сдвигается с «declarative vs body» на **«tests vs src»** — это новая D4.

| Роль | Кто | Делает | Не делает (enforcement) |
|---|---|---|---|
| **spec-author** | человек + главная сессия (`/spec`) | интервью → `change.md` + `criteria.md` | не пишет код и тесты |
| **test-author** | сабагент, отдельный контекст | из спеки пишет **красные** тесты (unit + integration + discovery), подтверждает красноту, коммитит их | не читает и не пишет `src/` бои́ реализуемого изменения; не редактирует criteria.md |
| **implementer** | сабагент | пишет код до зелёного тулчейна | **физически не может** редактировать `tests/` и `criteria.md` (hook §5.2); не завершает ход при красном гейте (SubagentStop §5.3) |
| **evaluator** | сабагент, **свежий контекст** | прогоняет полный гейт, **запускает приложение**, идёт по criteria.md, флипает чекбоксы с доказательствами, пишет `verdict.md` | не правит ни код, ни тесты (read-only + Bash) |

Анти-паттерны, которые эта раскладка закрывает (оба — самые задокументированные провалы
агентских циклов): **self-evaluation bias** (работник хвалит свою работу → evaluator всегда
в свежем контексте и не автор кода) и **collusion** (тест и код пишутся из одного понимания
→ test-author пишет тесты из спеки ДО кода, implementer тесты трогать не может — наш D3,
теперь и официальный гайдлайн Anthropic/OpenAI).

Уточнение к test-author в brownfield: читать существующий код (интерфейсы, фикстуры,
существующие тесты) — можно и нужно; запрет распространяется на новые бои́, которые в момент
написания тестов ещё не существуют (порядок цикла это гарантирует сам).

## §5. Enforcement: правила, которые нельзя нарушить

Иерархия — от совета к невозможности:

1. **Скиллы** (проза) — house style, «как принято». Нарушение возможно → страхуется уровнями ниже.
2. **Тулчейн** — `mypy` / `ruff check` / `ruff format --check` / `pytest` (набор и конфиг —
   из conventions block E, переносится из v2 как есть, включая `B006`, `B904`).
3. **Grep-гейты** (переносятся из v2 дословно): `# type: ignore` на content-модулях,
   `from __future__ import annotations`, `# noqa: F401` — плюс архитектурный grep-firewall
   (`test-architecture-rule`) в тестах самого приложения.
4. **Hooks** — новое в v3, закрывают провал 2:

### 5.1 Gate-скрипт — одна точка правды о «зелёном»

`.claude/tools/gate.py` (stdlib-only, как валидатор v2): прогоняет 2–3 и печатает
машиночитаемый вердикт (`GREEN` / список красного). Один скрипт используют: SubagentStop-hook
implementer'а, evaluator, `/accept-change` и человек руками. Никто не решает «зелено ли»
по-своему — это A-серия «одна точка правды», применённая к вердикту.

### 5.2 PreToolUse-hooks (блокируют ДО выполнения)

| Hook | Правило | Механизм |
|---|---|---|
| `criteria-guard` | в `criteria.md` разрешён только флип `[ ]`→`[x]`; любая правка текста пункта — deny | PreToolUse на Edit/Write: matcher по пути `**/criteria.md`; скрипт сравнивает old/new_string — допустим только checkbox-флип |
| `test-guard` | агент в роли implementer не может править `tests/**` | PreToolUse на Edit/Write по пути `tests/**` в контексте implementer-сабагента |
| `spec-guard` | `spec.md` и `archive/**` не правятся вне `/spec` и `/accept-change` | PreToolUse по пути `specs/**/spec.md`, `specs/**/archive/**` |

Механизм привязки hook'а к роли (test-guard) — деталь имплементации: проверить в актуальных
доках, доступно ли имя сабагента в payload hook'а; fallback — маркер-файл роли, который
выставляет команда перед диспатчем, а hook читает. Это первое, что Opus верифицирует (§10, WP3).

### 5.3 Stop-гейты (нельзя сказать «готово», не будучи готовым)

- **SubagentStop на implementer:** ход не завершается, пока `gate.py` красный (с потолком
  итераций, чтобы не зациклиться, — после N отказов hook пропускает завершение с пометкой
  ESCALATE в отчёте). Закрывает «verification gap» — агент рапортует до прогона.
- **Stop на главной сессии в `/implement`:** цикл не считается завершённым, пока
  `criteria.md` содержит `[ ]` ИЛИ `verdict.md` не написан — либо явная эскалация человеку.

### 5.4 Что переносится из v2 в гейты без изменений

Construct-smoke (`create_app()` + OpenAPI) как обязательная часть gate.py; Docker-tier
(testcontainers) — в evaluator-прогон, когда Docker доступен (иначе — явная пометка
`DOCKER SKIPPED` в verdict.md, не молчаливый пропуск — «no silent no-op» из A4).

## §6. Цикл: команды и протокол итераций

Три команды — весь воркфлоу (охват «ядро», upstream-стадии v2 переносятся потом):

### `/spec [<context>] [<описание>]`
Интерактивная. Интервью с человеком (AskUserQuestion по неоднозначностям — аналог
`/clarify` у Spec Kit и «interview → SPEC.md» у Anthropic): читает `spec.md` контекста
(что уже есть), задаёт вопросы, предлагает глубину S/M/L, пишет `change.md` + `criteria.md`.
Гейт на выходе: Acceptance criteria непусты и сформулированы как наблюдаемое поведение;
Verification отвечает «как доказать». Спека — на языке диалога с пользователем (русский);
это вход для человека, не для машины.

### `/implement <NNN-slug>`
Цикл. Шаги:

1. **test-author** (сабагент): тесты из criteria (каждому AC — минимум один тест, где это
   физически возможно; невозможное — явно в verdict как MANUAL), прогон — подтвердить
   **красное** (тест, зелёный до имплементации, подозрителен — либо критерий уже выполнен,
   либо тест пуст), **коммит красных тестов** (чекпоинт-практика: фиксирует контракт до кода).
2. **implementer** (сабагент): код до зелёного `gate.py`. Скиллы подгружаются авто-инвокацией
   (§7). Тесты и criteria — read-only (hooks). Внутренний потолок: 3 итерации на красный
   тест → ESCALATE (порог из v2, он себя оправдал).
3. **evaluator** (свежий сабагент): полный `gate.py` + запуск приложения + проход по
   criteria.md → флипы с доказательствами → `verdict.md` (по каждому AC: PASS/FAIL/MANUAL +
   доказательство; плюс общая секция: гейт, Docker-tier, замечания).
4. **Ветвление:** все AC зелёные → готово, человеку на `/accept-change`. Есть FAIL →
   verdict.md уходит новому implementer-диспатчу (шаг 2) с конкретикой провала. Потолок
   полного цикла: 3 прохода → эскалация человеку с verdict.md как отчётом.

Оркестрирует главная сессия (команды + сабагенты — решение зафиксировано); сабагенты
диспатчатся фоново там, где независимы (test-author для разных changes — параллельно,
внутри одного change цикл последователен).

### `/accept-change <NNN-slug>`
Гейт: `criteria.md` весь `[x]` + `gate.py` GREEN + verdict.md свежее кода (иначе — пересчёт
evaluator'ом). Действие: агент готовит diff вливания дельты в `spec.md` → человек ревьюит →
каталог в `archive/`. Единственная команда, которой hook разрешает писать в `spec.md`.

**Адверсариальный ревью-проход** (наследник §9-механики v2: body-blind верификация ассертов)
в ядро не входит — он становится опциональным шагом `/implement --adversarial` (отдельный
сабагент пытается опровергнуть силу тестов по чеклисту рецептов из `test-*` скиллов).
Механика v2 доказала ценность, но для простого ядра это тюнинг, не каркас.

## §7. Скиллы: ревизия + слияние 44 → ~13

Что делает ревизия (один проход, решение зафиксировано):
1. **Вычистить манифест-связку:** упоминания kind→skill диспатча, манифест-слайсов,
   «validator/scaffolder/runner» — всё это отсылки к оркестрации v2 (нарушение C1 задним
   числом). Human-onboarding тест C3 — критерий чистки.
2. **Слить группы** до гранулярности, которую агент выбирает сам (без реестра), с frontmatter
   `when`-триггерами для авто-подгрузки:

| Новый скилл | Поглощает | Примечание |
|---|---|---|
| `conventions` | себя (урезается) | пути/нейминг/store-profiles/substrate/тулчейн остаются; kind→skill реестр — удаляется |
| `architecture` | general-layered-architecture, general-python-package, general-imports-conventions | слои + пакеты + импорты — одна тема «куда что кладём» |
| `python-style` | general-typing-conventions, general-logging | сквозной стиль |
| `domain-model` | domain-entity, -value-object, -enum, -exception, -filter | данные домена |
| `domain-ports` | domain-repository-protocol, domain-capability-protocol, domain-service | контракты и сервисы |
| `application` | application-command, -query, pattern-compensating-tx, pattern-unit-of-work | CQRS + санкционированные try/except |
| `infra-persistence` | infra-sqlalchemy-repository, -table, infra-store-repository | polyglot-хранилища |
| `infra-integration` | infra-capability-adapter, infra-settings, infra-di-provider | адаптеры/настройки/DI |
| `restapi` | restapi-endpoint, -schema, -app-bootstrap, -auth-dependency, -error-responses, -file-transfer, -middleware | весь REST-слой |
| `testing-unit` | test-application-handler, test-domain-*, test-fake-repository, test-architecture-rule | + рецепты силы ассертов (§9-наследие) |
| `testing-integration` | test-repository-contract, test-store-repository-contract, test-restapi-endpoint, test-discovery-invariants, test-integration-* | + testcontainers-дисциплина |
| `meta-skill-author` | себя | формат обновляется под слитые скиллы |
| `test-principles` | себя | мета-тест каталога, переписывается под новую структуру |

3. **Сохранить дословно** всё выстраданное содержимое: три раунда аудита, рецепты силы
   ассертов, fake-семантика (копии + updated-лог), two-sub-template идиомы (auth-optional,
   relational-optional), запреты (`__future__`, type: ignore, ORM, cursor pagination...) —
   слияние меняет упаковку, не знание. Diff ревизии обязан быть проверяемым: перенесено/
   удалено-как-манифестное/переписано — по каждому куску.

Четырёхсекционный формат (`When to use / Templates / Rules / Hard stops`) сохраняется —
он не зависит от манифеста и хорошо работает на двух читателей.

## §9. Пример прохода (сквозной, для проверки дизайна на ощупь)

Изменение: «UC-16 — участник может закрыть action item» (реальная дельта из dry-run v2).

1. `/spec meetings "закрытие action item по UC-16"` → интервью (идемпотентность? кто вправе?)
   → `specs/meetings/changes/004-complete-action-item/change.md` (глубина S: Task + 3 AC)
   + `criteria.md`: AC-1 `POST /action-items/{id}/complete` от участника воркспейса → 200,
   статус DONE; AC-2 повторный вызов идемпотентен (200, статус не меняется); AC-3 чужой
   item → 404 без утечки существования.
2. `/implement 004-complete-action-item`:
   - test-author: 3 теста (unit на хендлер с fake-репо + endpoint-тест) → красные → коммит;
   - implementer: enum grows DONE, протокол grows `get_by_id/update`, хендлер, роут —
     скиллы `domain-model`/`application`/`restapi` подгрузились по `when`; gate.py GREEN;
   - evaluator: gate GREEN, приложение сконструировалось, OpenAPI содержит операцию,
     3/3 AC → `[x]` с именами тестов в verdict.md.
3. `/accept-change 004-...` → diff в `specs/meetings/spec.md` (операция «завершить action
   item» + инвариант идемпотентности) → человек одобрил → archive.

Сравнить с тем же изменением в v2 (architect-делта → validate → re-scaffold → drift-trigger
→ implementer → verify): цепочка v3 короче на два механизма (валидатор, планировщик) при
том же уровне доказательности. Это и есть проверяемое обещание v3.

## §11. S-серия принципов (замена B-серии; кандидаты в PRINCIPLES.md при WP1)

**S1 · Спека описывает поведение, не устройство.** *Trigger:* тянет записать в спеку имя
класса, путь, тип колонки. *Litmus:* это проверяемо снаружи работающей системы? Нет →
это Design notes (совет) или вообще решение implementer'а. *Why:* устройство — производная,
два источника правды снова разойдутся.

**S2 · Один формат, три глубины; ceremony по размеру diff'а.** *Trigger:* хочется сделать
секцию обязательной. *Litmus:* нужна ли она S-спеке из одного предложения? Нет → опциональна.
*Why:* обязательные секции — это обязательные поля v2 в новой одежде.

**S3 · Критерий — наблюдаемое поведение; чеклист append-only для агентов.** *Trigger:*
критерий формулируется про код («используется паттерн X») или агент хочет уточнить пункт.
*Do:* переформулировать через запуск системы; правка текста — только человеком. *Why:* A4 +
«ни один сценарий не выпадает молча» — то, ради чего жил манифест.

**S4 · Must-hold правило живёт в гейте, не в прозе.** *Trigger:* в скилл/спеку пишется
«никогда не делай X». *Litmus:* что физически произойдёт, когда агент всё-таки сделает X?
Если ответ «ничего» — правило не существует; добавь grep-гейт/hook или понизь до совета.
*Why:* провал 2 обоих прошлых поколений.

**S5 · Вердикт выносит не автор.** *Trigger:* агент, писавший код, отчитывается «критерии
выполнены». *Do:* вердикт валиден только из свежего контекста evaluator'а + gate.py.
*Why:* self-evaluation bias — самый задокументированный провал агентских циклов.

**S6 · Дельта вливается, спека компаундится.** *Trigger:* change принят. *Do:* archive-merge
в spec.md — немедленно, ревьюированно; changes/ не накапливает историю (история — git).
*Why:* одноразовые спеки — главное архитектурное сожаление Spec Kit.

## §12. Риски и открытые вопросы

1. **Blast-radius без графа.** Отвечаем grep'ом и чтением spec.md; на большом приложении
   может заболеть → тогда тонкий индекс (решение отложено сознательно, B1/earn-its-place).
2. **Merge дельты в spec.md — LLM-шаг с человеком-ревьюером.** Качество вливания не
   детерминировано; страховка — маленькие дельты (S2) + git-diff ревью. Если spec.md начнёт
   гнить — вводить структуру секций spec.md жёстче (но не раньше боли).
3. **Роль-специфичные hooks** — механизм не верифицирован против текущих доков (первое
   действие WP3). Fallback (маркер-файл) описан.
4. **Стоимость цикла.** Три сабагента на change + повторные проходы; для S-change это может
   быть дороже, чем «просто попросить Claude». Митигация: S-глубина позволяет `/implement`
   схлопнуть test-author и evaluator в один диспатч? — НЕТ (ломает D3/S5); вместо этого
   принять оверхед как цену доказательности, мерить на WP7.
5. **Длинные сабагенты** (F-021 v2: смерть на ~50 мин). Митигация архитектурой: в v3 нет
   единственного долгого scaffold-прохода — работа нарезана по change'ам; если implementer
   одного change живёт >30 мин, change слишком большой (сигнал к разрезанию спеки).
6. **Upstream-стадии** (PDF → use-cases → вопросы BA) — вне охвата ядра; analyst-механика v2
   концептуально совместима (её выход станет `/spec`-входом), перенос — после WP7.
