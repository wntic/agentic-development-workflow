FINDINGS / CORRECTIONS
----------------------
* CORRECTION to an earlier (wrong) in-chat analysis. I claimed an added protocol method with no
  in-context consumer would produce NO mypy-red (structural protocols + "untyped DI"). WRONG: the DI
  container types the provider as `providers.Provider[IUserRepository] = providers.Factory(
  UserRepository, ...)`, and dependency-injector ships its own stubs, so mypy DOES check conformance —
  the missing method reds `containers.py:48`. The DI-container annotation is the use-site that forces
  conformance even with no business caller.
* But the red surfaces at containers.py (GLUE, scaffolder-owned), while the FIX belongs in the repo
  body (implementer-owned). The runner's textual NIE scan listed nothing (the body has no
  NotImplementedError), so /verify would have drained 0 items and only hit the red at the final
  whole-tree gate with no per-node entry to dispatch. That is exactly the gap the new drift trigger
  closes — it attributes the drift to the body file via the graph, not by parsing mypy messages.
* Drift detection v1 catches METHOD-PRESENCE drift (added/removed protocol methods on repo/capability
  implementers). A same-name SIGNATURE change (renamed param, changed type) is NOT caught by the
  per-node trigger; it still falls only to the final whole-tree mypy gate. Acceptable increment;
  earn-its-place for the trigger logic (built for the case that arises). Worth a follow-up if
  signature-drift deltas become common.
* No unit-level protocol-conformance test exists (test-repository-contract is Postgres/integration,
  absent without Docker). The DI-container mypy check is what catches conformance in the Docker-less
  gate — which is why the drift surfaced there at all. A unit conformance check would make it explicit.

KNOWN FRONTIER (blocks the FULL Tickets forward proof) — UNBUILT, spec §13 «потом» / §15
-----------------------------------------------------------------------------------------
Cross-epic scaffold-time resolution. A bounded context is one manifest (spec §7); Tickets is a
SEPARATE context from Identity (they do not change together) that draws an inbound cross-epic edge
`auth:IUserRepository.get_by_id`. At scaffold time that edge must resolve to an import of the
already-scaffolded identity code in the same package — and NONE of that is built:
  - validator: treats `:`-bearing refs as a WARNING ("left unresolved, no other manifests yet"),
    does not resolve them across manifests.
  - conventions: no cross-epic → import derivation.
  - scaffolder: no multi-manifest / second-manifest-into-an-existing-package handling.
So the consuming context (Tickets) cannot yet be scaffolded into the identity package, which is why
the delta proof used the cross-epic EXPOSURE (the upstream half, on identity) rather than the full
Tickets build. Building this is the multi-manifest/cross-context frontier the spec defers to the
packaging/marketplace phase (§15) and §14 open questions #5/#7 (role placement, cross-epic notation).
